## Abstract

> AI agents can write migrations, but production changes need guardrails. This
> live demonstration walks through an agent-assisted PostgreSQL workflow using
> Tiger Cloud and the Tiger CLI: provisioning an isolated development service,
> generating versioned migrations, and testing correctness and performance
> before human-approved production deployment. We'll cover scoped access,
> automated checks, lock and rewrite detection, deployment monitoring, and
> rollback criteria. Attendees will leave with a practical blueprint for
> accelerating database delivery without giving agents unchecked authority over
> production.

## What we mean by "agentic workload"

An **agentic workload** is computing work generated by AI agents rather than
directly by humans or by fixed, pre-programmed application logic. The agent
receives a goal, then decides on its own which actions to take, often over many
steps: calling tools, querying data, writing and running code, checking
results, and adjusting its plan until the goal is met.

Compared with traditional workloads, it has a few defining traits:

- **Non-deterministic request patterns.** The sequence and shape of operations
  aren't known in advance. The agent chooses them at runtime from intermediate
  results.
- **Iterative loops.** One user request can fan out into dozens or hundreds of
  model calls and tool calls (reason, act, observe, repeat).
- **Bursty and parallel.** Agents may spawn sub-agents or run many exploratory
  actions at once, then go quiet.
- **Machine-generated queries.** Queries are written by a model, so they're
  often ad hoc, unoptimized, repetitive, or exploratory (schema introspection,
  `SELECT *`, trial-and-error).
- **Mixed state needs.** Agents need short-lived scratch space (branches, temp
  tables, sandboxes) alongside durable memory such as conversation history,
  embeddings, and task state.

**On the database side,** this is why the term matters. A database serving
agents sees far more connections and queries per "user intent" than an OLTP app
does. It also needs strong guardrails: least-privilege roles, statement
timeouts, row limits, and read replicas or forks so an agent can experiment
without touching production. It benefits from fast copy-on-write branching,
vector search alongside relational data, and good observability so you can
trace which agent issued which query. Capacity planning shifts from "requests
per user" to "steps per task × concurrent agents."

In short, an agentic workload is autonomous, multi-step, model-driven activity,
and its resource usage is far less predictable than human-driven or scripted
traffic.

### How this demo maps to it

| Trait | Where it shows up here |
|---|---|
| Agent chooses its own steps | In `migration-test`, the consultant gets read-only tools on the ephemeral clone and decides which catalog lookups / queries to run before answering. |
| Iterative loop | Reason → tool call → observe → repeat, bounded by a per-run tool-call budget. Every step is recorded in the run's "Agent trace". |
| Machine-generated queries | The agent writes its own SQL (`run_readonly_query`). |
| Guardrails | Dedicated `agent_ro` role (SELECT only, `default_transaction_read_only`), `READ ONLY` transaction, statement timeout, row limit, single-statement only, call budget. Ephemeral service only, never prod. |
| Scratch space vs. durable memory | Ephemeral Tiger service per run (scratch) + the RAG store and `agent/knowledge/decisions/` (memory). |

`migration-review` stays deliberately tool-less: it touches no database.

## What this commits us to (demo-time deliverables)

- [ ] **Provision an isolated dev service** — ephemeral Tiger Cloud service via
      Tiger CLI, created per run, torn down after.
- [ ] **Generate versioned migrations** — the ORM (Prisma) autogenerates
      versioned migration SQL; the AI agent reads it and proposes alternatives.
- [ ] **Test correctness and performance in dev** — candidate approaches run in
      ephemeral dev services (scaled 1M boundary, fast), evidence collected.
- [ ] **Automated checks + lock/rewrite detection** — guardrail scripts that
      fail CI on an `ACCESS EXCLUSIVE` / full-table-rewrite hazard.
- [ ] **Scoped access** — the agent is dev-scoped, never holds prod credentials.
- [ ] **Human-approved production deployment** — gated GitHub Environment; the
      agent recommends, the human decides.
- [ ] **Deployment monitoring** — committed deliverable (Datadog). *Deferred to
      a later build phase, not dropped.*
- [ ] **Rollback criteria** — committed deliverable. *Later phase, not dropped.*

## Framing notes

- **The on-stage story is the guardrailed workflow** (agent proposes → tested in
  dev → human approves → safe prod), told through Tiger Cloud + the Tiger CLI +
  the guardrails. Narrate the workflow, not the IAM policy.
- **The implementation is fully AWS-native and that's a strength**, not a
  distraction: AgentCore (the AI runtime), Amazon Nova Pro (default model),
  CodeBuild (the GitHub Actions runner), OpenTofu, Secrets Manager. Built richly
  AWS-native under the hood (AWS Community Builder resource access), kept as the
  foundation rather than the headline.
- **Candidate migration approaches run live in dev, in parallel, and fast** (at
  the 1M scaled boundary). Which candidate "wins" is a demo-time human decision,
  not a build-time blocker — the candidate migrations are authored last.

## Deferred / open (not blocking the build)

- Which candidate(s) are the live centerpiece — decided at demo time (D /
  hypertable is the current favorite, not locked).
